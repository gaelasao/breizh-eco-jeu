# Sécurité — breizh-eco-jeu

## Signaler une faille

Ne pas ouvrir de ticket public (issue) : ce dépôt est public, et une faille décrite dans un ticket est lue par tous avant d'être corrigée. Le signalement privé de GitHub (« Report a vulnerability ») n'est pas ouvert à ce jour : c'est à l'éditeur de le décider. **Canal** : écrire à l'éditeur, Breizhcosystem, à l'adresse de contact publiée sur la page « Mentions légales » de Breizhcosystem (`<Breizhcosystem>/mentions-legales`), objet « Sécurité », sans données réelles d'une entreprise ni mot de passe, et sans rendre le problème public avant le correctif. Le même canal est donné dans `LISEZMOI.txt` de chaque paquet et sur la page « Licences et crédits » du jeu (`scripts/paquets.test.ts` vérifie que les trois disent la même chose). Restent à créer par l'éditeur : une adresse dédiée à la sécurité et `/.well-known/security.txt` (RFC 9116) sur Breizhcosystem. Traitement d'un signalement, divulgation coordonnée et notification des vulnérabilités activement exploitées (article 14 du règlement (UE) 2024/2847) : [docs/conformite/DIVULGATION-COORDONNEE.md](docs/conformite/DIVULGATION-COORDONNEE.md).

Chaque paquet contient sa nomenclature logicielle `app/SBOM.cdx.json` (CycloneDX 1.5 : dépendances npm d'exécution tirées du verrou, Node.js embarqué avec le SHA-256 de son archive officielle, polices et icônes avec le SHA-256 du fichier livré) ; obligatoire pour une publication.

## Exigences (chap. 13, OWASP API Top 10, OWASP Multi-Tenant)

- Authentification, sessions, rôles et périmètres **contrôlés côté serveur** sur chaque objet, y compris recherche, fichiers, caches, tâches différées. Un utilisateur sans droit ne reçoit pas l'objet, même par URL directe ou API.
- Administrateurs : validation en deux étapes (TOTP) **obligatoire en ligne** (`LB_EN_LIGNE=1`, refus `403 deux_etapes_requise` tant qu'elle n'est pas activée) ; sur un poste local ou le réseau du bureau, elle est proposée mais pas imposée (l'accès suppose déjà l'ordinateur ou le réseau de l'entreprise). Accès techniques limités, temporaires, journalisés. L'éditeur n'a ni compte ni accès aux contenus.
- Secrets : jamais dans le code, le dépôt, le navigateur, les journaux, ni les instructions envoyées à un modèle. `.env` ignoré par git ; scan gitleaks en CI.
- Chaîne de fabrication (GitHub Actions) : actions épinglées par empreinte de commit complète (version en commentaire, tenue à jour par Dependabot), `npm ci --ignore-scripts` partout et `ignore-scripts=true` dans `.npmrc` (aucun script d'installation, même pour un `npm install` à la main ; aucune dépendance n'en demande), **quarantaine de 7 jours** avant d'adopter une nouvelle version (14 pour une majeure) : `cooldown` de Dependabot, et même règle pour une mise à jour faite à la main ; fabrication des paquets avec le seul droit de lecture ; la publication (`contents: write`) est un job séparé qui ne lance ni le code du dépôt ni npm (`scripts/chaine-ci.test.ts`). La version GitHub n'est pas la référence de distribution : c'est la publication signée hors ligne par l'éditeur.
- Connecteurs : lecture seule par défaut, écriture = capacité explicite ; révocation immédiate et visible. « Se connecter avec… » : le sens se choisit **avant** la connexion, le jeu ne demande au relais que la **lecture** (`droits: "lecture"`, portée minimale) sauf synchro qui écrit (`"ecriture"`) ; une connexion en lecture seule ne peut pas servir à une synchro qui écrit (`409 droits_lecture`, il faut se reconnecter).
- **« Se connecter avec… »** (HubSpot, Google, Microsoft, Notion, Airtable, Pipedrive, Sellsy, Shopify, WooCommerce) passe par le **relais de connexion de Breizhcosystem**, qui garde le secret de l'application de l'éditeur : les jetons ne transitent par Breizhcosystem qu'au moment de la connexion (remis UNE fois au jeu, 10 min au plus, chiffrés en mémoire) et de chaque renouvellement, **sans jamais y être enregistrés** ; les **données de l'entreprise ne passent jamais par Breizhcosystem** : le jeu appelle l'outil directement. Côté jeu : le secret d'attente reste sur le serveur du jeu (le navigateur ne reçoit qu'une adresse à ouvrir et une référence `oauth:…` à usage unique, 30 min) ; aucun jeton ni secret d'attente dans une adresse ; la page de connexion renvoyée par le relais doit être en https sur l'hôte attendu de l'outil (ou de la boutique Shopify / du site WooCommerce saisis), sinon la connexion est annulée ; jetons relus (caractères visibles seulement, 8000 au plus), informations complémentaires connues seulement (domaine `*.pipedrive.com`, boutique `*.myshopify.com`, clé `ck_…`, site https) ; secret enregistré `{"oauth":{…}}` chiffré en AES-256-GCM comme les autres, jamais renvoyé au navigateur ; un secret collé qui l'imiterait est refusé ; renouvellement quand le jeton expire dans moins de 2 minutes, et une seule fois sur un refus 401 de l'outil ; rotation enregistrée ; routes réservées à l'administrateur. Adresse Shopify `^[a-z0-9][a-z0-9-]*\.myshopify\.com$`, site WooCommerce vérifié par l'anti-SSRF (`verifierUrl`). L'onglet de connexion est ouvert sans lien vers le jeu (`opener` coupé).
- Mode avancé : connecteurs avec les identifiants de l'ENTREPRISE (jeton de l'outil, script de sa feuille Google, application de son annuaire Microsoft), sans aucune application de l'éditeur. Google Sheets : secret aléatoire de 192 bits généré par le jeu, exigé par le script, transmis dans le corps (jamais dans l'adresse), seule la redirection vers script.googleusercontent.com est suivie. Microsoft 365 : connexion par code d'appareil (mot de passe saisi chez Microsoft seulement), le navigateur ne reçoit qu'une référence à usage unique, jeton de rafraîchissement chiffré au repos et renouvelé à chaque usage, hôtes fixes login.microsoftonline.com et graph.microsoft.com, page de connexion vérifiée (microsoft.com).
- FEC (comptabilité) : lu en mémoire, seuls des totaux sont gardés dans la fiche entreprise ; ni le fichier ni les écritures ni les noms de tiers ne sont enregistrés ou envoyés ; réservé à l'administrateur.
- Webhooks : entrée par secret au porteur (`Authorization: Bearer`, comme une clé d'API, sous HTTPS) ou signature horodatée `X-LB-Signature: t=…,v1=…` (HMAC-SHA256 de « t.corps », 5 minutes d'écart au plus, rejeu refusé tant que la signature est valable ; forme sans horodatage refusée) ; écriture idempotente par identifiant externe (un même enregistrement reçu deux fois ne crée pas de doublon) ; envois du jeu signés avec une clé dérivée distincte (jamais acceptée en entrée). Limite connue : la mémoire des signatures vues est perdue au redémarrage (un rejeu reste borné aux 5 minutes). URLs sortantes filtrées (SSRF, adresse revérifiée à la connexion).
- Notifications : minimum d'information sensible, lien vers l'espace authentifié.
- Sauvegardes chiffrées, séparées, testées par restauration (cible : quotidienne, RPO 24 h, RTO 8 h — à mesurer).
- Données personnelles : pas de géolocalisation continue, pas de classement de salariés. Santé : seul le motif d'absence « maladie » du planning peut être saisi (donnée relative à la santé, sans diagnostic ; voir `docs/conformite/`). Le **motif** d'une absence (congé, maladie, formation) n'est vu et saisi que par les profils qui ont le droit RH « Voir et saisir les motifs d'absence » (par défaut : les administrateurs ; contrôle côté serveur, planning, fiche du jour, réponses de l'API et MCP) ; les autres voient « Absence » et ne peuvent saisir que « Absence » (le motif déjà saisi par les RH est gardé). Le journal n'écrit jamais le motif. Baromètre d'équipe réellement anonyme : réponses hors du monde, sans nom ni heure ni lien avec l'invitation, publiées par lots d'au moins 5, effacées après 13 mois.
- Revue de sécurité indépendante avant toute entreprise réelle.

## Passerelle (installation locale, une entreprise)

- Une installation = une entreprise. **L'éditeur n'a ni compte, ni télémétrie, ni accès aux données**, et aucune donnée de l'entreprise ne lui est envoyée. Ce qui peut joindre son serveur (Breizhcosystem), seulement sur un geste de l'entreprise : le réseau Breizhcosystem (partage coché dans le jeu), le **relais « Se connecter avec… »** (jetons de l'outil à la connexion et à chaque renouvellement, IP, adresse du jeu ; jamais contacté à l'ouverture de « Connecter mes données », seulement au clic), la liste publique des versions (IP seulement). Tout est listé dans Réglages → Confidentialité. Seul canal de l'éditeur vers une installation : les **mises à jour, lancées par l'entreprise et signées hors ligne** (voir « Chaîne de publication »).
- Écoute sur `127.0.0.1` par défaut. Réseau local : `HOST=0.0.0.0`. Internet : uniquement derrière un proxy HTTPS (mode en ligne ci-dessous).
- **Mode équipe** (réseau du bureau) : fermé par défaut ; ouvert ou fermé seulement par un administrateur sur l'ordinateur lui-même ; noms acceptés = adresses IP + nom de la machine ; http sans chiffrement sur le réseau local (avertissement affiché, à proscrire sur un Wi-Fi public). Lancement automatique : fichier de session de l'utilisateur au contenu fixe (chemins échappés), sans droits administrateur.
- **Anti DNS rebinding** : seuls les noms `localhost`, les adresses IP et les noms déclarés (`LB_HOTES`, `LB_ORIGINE`) sont servis (sinon 421).
- **Comptes locaux** : mot de passe ≥ 10 caractères (refus des plus courants et de l'identifiant), haché **scrypt** (N=2^15, r=8, p=1, sel 16 o), comparaison à temps constant, identifiant inconnu = même calcul et même message. 5 échecs → 15 min de blocage par paire (identifiant, adresse du client ; préfixe /64 en IPv6) : connaître un identifiant ne permet pas de bloquer son titulaire, qui se connecte d'une autre adresse. Toutes adresses confondues, au-delà de 30 échecs par heure sur un identifiant, chaque essai attend de plus en plus (0,5 s puis jusqu'à 8 s) sans refuser le bon mot de passe ; 40 essais / 10 min par adresse. Même règle pour le code de secours.
- **Installation** et **réinitialisation sur place** : uniquement depuis l'ordinateur lui-même (adresse de bouclage, nom d'hôte local, sans en-tête de proxy). Une seule installation.
- **Invitations** : jeton 256 bits, empreinte SHA-256 seule enregistrée, 7 jours, usage unique ; l'administrateur ne connaît jamais le mot de passe.
- **Code de secours** : ~100 bits, montré une fois, empreinte seule enregistrée, consommé et remplacé à l'usage. `npm run secours` : jeton 15 min écrit dans le dossier des données (preuve d'accès physique).
- Changement de mot de passe, désactivation ou retrait : **toutes les autres sessions du compte tombent** (version du compte vérifiée à chaque requête). Le dernier administrateur actif ne peut pas être retiré.
- **Voir comme** : aperçu en lecture seule (toute écriture refusée, 409).
- Mode démonstration (`npm run demo`) seulement : profils fictifs sans mot de passe, en mémoire.
- CSP stricte (`script-src 'self'`, aucun script ni style inline), `nosniff`, `frame-ancestors 'none'`, `no-referrer`.
- Cookie de session aléatoire 256 bits, `HttpOnly; SameSite=Strict`, expiration glissante (8 h), nouvel identifiant à chaque connexion.
- Écritures : en-tête `X-LB-Requete` obligatoire + contrôle `Origin` (anti-CSRF), JSON uniquement, corps ≤ 1,1 Mo (40 Mo pour une restauration).
- Fichiers statiques servis depuis une liste blanche construite au démarrage : aucun chemin dérivé de l'URL.
- Périmètre vérifié sur chaque objet, chaque référence (un lien vers un objet hors périmètre est masqué) et chaque action ; 404 indifférencié.
- Données au repos : fichiers 0600, dossier 0700 ; jetons des outils et adresse du webhook sortant (qui donne accès, à elle seule, au scénario Make ou Zapier ; montrée au navigateur réduite à son hôte) en AES-256-GCM ; jeu en ligne : la clé des secrets n'est pas dans le dossier des données mais dans un identifiant systemd chiffré par la clé du serveur (`systemd-creds --with-key=host`, `LoadCredentialEncrypted`, à défaut fichier réservé à root dans `/etc/living-business`), remis au seul service à son démarrage ; le service refuse de démarrer sans lui (`LB_CLE_HORS_DONNEES=1`) plutôt que de créer une clé neuve ; une copie de `/var/lib/living-business` ou des sauvegardes ne suffit pas à lire les jetons ; export chiffré par phrase (scrypt + AES-256-GCM). **Export complet** : depuis l'écran seulement (refusé avec une clé d'API), mot de passe puis code de validation redemandés, phrase de 12 caractères au moins ; par défaut SANS la clé des secrets (jetons et secrets TOTP y restent chiffrés par la clé de l'installation : illisibles ailleurs, effacés à une restauration ailleurs) ; « Inclure les accès » pour migrer, phrase de 16 caractères au moins. Chaque export est au journal (`sauvegarde.exportee`) et signalé aux autres administrateurs (bandeau jusqu'à « J'ai vu »).
- Import CSV : taille, lignes et colonnes bornées, valeurs validées par l'univers, empreinte anti-double import.
- **Paquets téléchargeables** : Node.js officiel téléchargé en HTTPS depuis nodejs.org et vérifié contre `SHASUMS256.txt`, lui-même signé par un publieur de Node.js dont la clé est épinglée dans `scripts/node-cles-publication.asc` (signature OpenPGP revérifiée à chaque fabrication, cache compris, sans gpg : `scripts/openpgp.ts`) — un nodejs.org ou un CDN compromis ne suffit pas (refus sinon) ; seul le binaire et sa licence sont gardés ; ni tests, ni données, ni dépendances de développement dans le paquet ; une **publication** ne se fabrique que sur un commit étiqueté `vX.Y.Z` avec une copie de travail propre, depuis les sources exportées du commit (`git archive`, hors du dossier de travail synchronisé) et des dépendances réinstallées depuis le verrou (`npm ci --omit=dev --ignore-scripts`), avec `PROVENANCE.txt` (commit, étiquette, empreinte du verrou) ; `scripts/signer-publication.ts` ne signe que sur ce même commit, copie propre, et refuse des paquets d'un autre commit ou d'essai (`--essai` → `dist/essai/`) (`scripts/provenance.test.ts`) ; empreintes SHA-256 des paquets publiées (`SHA256SUMS.txt`). Le lanceur n'ouvre dans le navigateur qu'une adresse `http://127.0.0.1:<port>/…` (pas d'interpréteur de commandes) ; une seule instance par dossier de données. Adresse de Breizhcosystem préréglée (`--nexus`) : https seulement, réduite à l'origine, écrite dans `app/package.json` (jamais dans un script de lancement), revérifiée par le jeu à chaque appel. Lanceurs Mac et Windows pas encore signés par Apple ni Microsoft : `LISEZMOI.txt` ne décrit le passage de Gatekeeper ou SmartScreen que pour un paquet téléchargé sur la page « Télécharger » de Breizhcosystem (mise en garde d'abord : un fichier reçu par e-mail ou trouvé ailleurs se supprime), et Réglages › À propos ne donne que le lien de cette page (construit par le serveur, https, origine du Breizhcosystem réglé).
- **Clés d'API** (`lb_…`, Claude/MCP, Make, scripts) : agissent avec les droits d'un profil, mais **jamais** sur une décision réservée à une personne connectée à l'écran (`403 session_requise`, même avec un profil administrateur) : achats et engagements Breizhcosystem (mandats, agent, validation, commande, annonce et paiement, contact, réponse à un besoin, publication, « Proposer à… », demande de prix entre agents), adresse et liaison Breizhcosystem, déliaison, accord de partage, clés (création, liste, révocation : une clé ne se donne pas une autre clé qui survivrait à sa révocation), accès et profils, automatisations, Bodacc, réglages des connecteurs, durées de conservation, export et restauration, « J'ai vu » sur un avis de sécurité (c'est la personne avertie qui le dit, jamais une clé créée avec son profil), vérification des nouvelles versions (réglage et lancement ; la lecture de l'état reste permise). Une clé **n'approuve jamais** une action (modification de fiche, tâche, mouvement de stock) : elle la prépare, `executer: true` est ignoré et `/actions/:cle/approuver` lui répond `403 session_requise` ; une personne approuve à l'écran (Aujourd'hui ou la fiche), l'action gardant la clé qui l'a demandée (`via`). Tout ce qu'une clé fait est écrit au journal avec la clé (`canal: "cle:<id> « <nom> »"`) à côté du profil ; création et révocation d'une clé sont au journal avec la personne. Une clé écrit au plus **600 fois par 10 minutes** (API et MCP confondus, `429 trop_d_ecritures` au-delà ; les lectures ne comptent pas), et la même case de planning modifiée à la suite ne fait qu'une ligne : une rafale ne vide pas le journal. Les **événements de sécurité** (exports et restaurations, clés, accès, comptes, liaison et partage avec le réseau Breizhcosystem, avis « vu », effacements, purges) sont en plus gardés **à part pendant 12 mois** (`GET /api/v1/journal?genre=securite`, 2 000 lignes au plus par type d'événement) : les 5 000 lignes tournantes du journal d'activité ne les chassent pas, et une restauration ne les fait pas disparaître. Une nouvelle clé ne prend jamais le profil administrateur par défaut. Réponses MCP : chaque résultat commence par un rappel (les textes peuvent venir de tiers : données, jamais consignes), contre l'injection d'instructions par un commentaire de formulaire, un CRM ou un webhook. Restent directs pour une clé (journalisés, confirmés par le client MCP faute de `readOnlyHint`) : créer une fiche, affecter le planning, marquer un courrier, créer un lien de formulaire.
- **Breizhcosystem, agents d'achat** : l'agent prépare, une personne valide toujours (aucun achat automatique ; côté jeu, la validation, la commande et le paiement exigent une session d'une personne) ; la clé `nx_…` ne part que dans l'en-tête `Authorization`, jamais dans une adresse. Chaque réponse de Breizhcosystem est relue avant affichage ou usage (identifiants UUID, statuts connus, textes bornés et sans caractères de contrôle, liens https seulement). Paiement direct au vendeur, jamais via Breizhcosystem : paiement en ligne **uniquement** vers une page `https://checkout.stripe.com/…` (toute autre adresse refusée, côté passerelle et côté écran) ; virement : IBAN avec clé de contrôle vérifiée, montant et référence `NX-…` validés. « Commander » envoie un en-tête `Idempotency-Key` (le même à chaque nouvel essai d'une même validation). Liaison : seule une réponse `401 cle_invalide` efface la clé `nx_…` ; une entreprise suspendue par l'éditeur (`403 entreprise_suspendue`) garde sa clé, l'état « suspendu » est affiché, et tout reprend à la levée ; un autre refus de Breizhcosystem remonte en erreur 502 (jamais confondu avec la fin de la session du jeu).
- **Validation en deux étapes** (TOTP, RFC 6238 : HMAC-SHA-1, 6 chiffres, 30 s, ±1 pas) : secret de 160 bits chiffré au repos (AES-256-GCM, clé des secrets), jamais renvoyé après l'activation ni journalisé ; activation confirmée par un premier code ; un code déjà accepté est refusé (dernier pas retenu) ; 8 codes de récupération de 40 bits à usage unique (empreintes SHA-256 seules, comparaison à temps constant) ; après le mot de passe, la session reste « en attente du code » (5 min, aucun accès) ; 5 codes faux → 15 min de blocage du compte, 40 essais / 10 min par adresse ; activation = les autres sessions du compte tombent ; désactivation = mot de passe ET code valable. Le code de secours, `npm run secours` / `sudo living-business-secours` et un nouveau lien d'invitation (créé par un administrateur) la remettent à zéro (téléphone perdu). Le QR code est dessiné par le jeu (SVG en adresse `data:`), sans service extérieur. Les sauvegardes exportées gardent le secret chiffré ; à la restauration il est ré-chiffré pour la nouvelle installation (illisible : désactivé).
- Application installable : service worker minimal, pages toujours par le réseau ; rien n'est mis en cache hormis la page « Pas de connexion », sa feuille de style et l'icône — **jamais** `/api/`, `/mcp`, ni aucune donnée de l'entreprise.

## Mode en ligne (serveur de l'entreprise, `LB_EN_LIGNE=1`)

Le jeu tourne sur le serveur loué par l'entreprise (Ubuntu, `deploiement/installer-jeu.sh`), derrière Caddy (HTTPS Let's Encrypt, HSTS) sur la même machine, en service systemd isolé (utilisateur dédié, `ProtectSystem=strict`, écriture limitée au dossier des données, écoute `127.0.0.1` seulement, appels système filtrés `@system-service` sans `@privileged`, `/proc` réduit aux processus du jeu, ni horloge, ni nom d'hôte, ni setuid, ni temps réel ; score affiché par la CI avec `systemd-analyze security`). API d'administration de Caddy coupée (`admin off`) : aucun processus local, le jeu compris, ne peut recharger la configuration de Caddy ni lire ses clés TLS par cette voie ; la configuration s'applique par redémarrage, seulement quand elle change. Caddy, seul programme exposé à Internet, vient du **dépôt officiel du projet** (Cloudsmith) et non du paquet `universe` d'Ubuntu (2.6.2, correctifs non garantis) : clé de signature du projet inscrite dans le script signé (empreinte `65760C51 EDEA2017 CEA2CA15 155B6D79 CA56EA34`, contrôlée par `scripts/installateur.test.ts`), paquet d'Ubuntu écarté (priorité -1), mises à jour de sécurité automatiques (unattended-upgrades) ; réévalué à chaque passage, un serveur déjà installé y passe à sa mise à jour suivante en gardant son Caddyfile. rclone (copie sortante facultative, jamais à l'écoute) reste le paquet d'Ubuntu. L'éditeur n'y a ni compte ni accès ; il ne peut y faire exécuter que des publications **signées par sa clé hors ligne**, quand l'administrateur lance la mise à jour ou chaque nuit s'il a accepté les mises à jour automatiques à l'installation (`living-business-mise-a-jour.timer`, `sudo living-business-mise-a-jour-auto oui|non`). SSH : clé seulement dès qu'une clé est installée (`00-living-business.conf`, lu avant `50-cloud-init.conf`), refait et contrôlé par `sshd -T` à chaque passage. Copie hors serveur : rclone tourne sans root (utilisateur éphémère `DynamicUser`, seul droit gardé = lire, ne voit de `/var` que les sauvegardes, clé des secrets, identifiants systemd, clés SSH et TLS masqués, aucune écriture) ; la phrase de chiffrement passe par l'entrée standard (`rclone obscure -`). Identifiants S3 et phrase restent forcément sur le serveur : contre un rançongiciel, l'installateur recommande un conteneur **versionné et verrouillé** (Object Lock, mode conformité, rétention 31 jours) avec une clé **sans droit d'effacement** ; dans ce mode (`/etc/living-business/copie-verrouillee`), le serveur n'efface rien, la règle de cycle de vie du conteneur retire les copies de plus de 31 jours. Sinon, le serveur efface lui-même les copies de plus de 31 jours chaque nuit.

- **Première installation à distance** : au démarrage, s'il n'existe aucun compte, un code de 256 bits (base64url, 43 caractères) est écrit dans `${LB_DONNEES}/installation.txt` (0600, écriture atomique) ; seule son empreinte SHA-256 reste en mémoire ; il n'apparaît dans aucune réponse ni aucun journal. L'installateur affiche `${LB_ORIGINE}/installation#<code>` : le code est dans le **fragment** (jamais envoyé dans l'adresse, donc absent des journaux du proxy et de l'en-tête Referer), la page le lit puis le retire aussitôt de la barre d'adresse et de l'historique, et l'envoie seulement dans l'en-tête `X-LB-Installation` des routes d'installation (`/installation`, `/installation/restaurer`, `/installation/verifier`). Comparaison à temps constant ; 5 codes faux par adresse → 15 min de blocage ; code et fichier détruits dès l'installation (ou la restauration) réussie ; tant que rien n'est installé, le code du fichier est repris au redémarrage (s'il est intact et lisible par le seul utilisateur du service ; sinon un nouveau est créé). Pour l'annuler : supprimer le fichier et redémarrer le service. Sur place (bouclage, sans en-tête de proxy) : sans code, comme en local. Hors mode en ligne : installation **toujours** sur place uniquement.
- **Secours** : `sudo living-business-secours` (utilisateur du service, preuve d'accès au serveur) crée la demande de 15 min dans le dossier des données et affiche `${LB_ORIGINE}/secours/<jeton>` ; en mode en ligne seulement, ce lien est accepté à distance (jeton 256 bits, empreinte seule, usage unique, 5 jetons faux par adresse → 15 min de blocage).
- **Administrateurs** : validation en deux étapes **obligatoire** ; un administrateur qui ne l'a pas activée est envoyé à l'activation juste après la connexion et toute autre route lui répond `403 deux_etapes_requise` (droits d'administration donnés plus tard : même chose dès la requête suivante). Recommandée pour les autres comptes.
- **Proxy** (`LB_PROXY=1`) : l'adresse du client pour les limites d'essais est la **dernière** valeur de `X-Forwarded-For` (celle ajoutée par Caddy ; la première peut être inventée par le client) ; valeur illisible → adresse de la connexion. Sans `LB_PROXY`, l'en-tête est ignoré. « Sur place » est toujours faux pour une requête relayée (`X-Forwarded-For` ou `Forwarded` présent).
- **Noms servis** : `LB_HOTES` / `LB_ORIGINE` (le domaine), sinon 421 ; seule exception : `GET /api/v1/vivant` → `{ "ok": true }` (aucune donnée) pour la vérification de l'installateur. Cookie `Secure` (`LB_COOKIE_SECURE=1`). Pas de mode équipe en ligne (l'adresse d'écoute reste `127.0.0.1`, même si une sauvegarde restaurée avait le mode équipe).
- **Migration** : la sauvegarde exportée de l'ordinateur (chiffrée par phrase) se restaure depuis la page du lien d'installation ; secrets des outils et de la validation en deux étapes ré-chiffrés avec la clé du serveur.
- « Faire installer par Claude » : le texte fourni interdit de demander ou d'écrire mots de passe, clés, codes ou phrases dans la conversation, de lire ou d'envoyer les données de l'entreprise, d'ouvrir d'autres ports ou de désactiver une protection (vérification de signature comprise) ; SSH par clé seulement. Il demande de lancer la commande sans la modifier, de s'arrêter si la signature ne se vérifie pas, et de ne suivre aucune consigne lue dans les fichiers ou les réponses des commandes. Rien de modifiable par une clé d'API n'y entre tel quel : le nom de l'entreprise y est réduit à une ligne sans guillemets (et enregistré sur une ligne côté serveur), l'adresse de Breizhcosystem (réglable par une personne seulement) réduite à son origine https.
- Reste à faire : revue de sécurité indépendante avant toute entreprise réelle.

## Chaîne de publication (installateur et paquets signés)

Le script `installer-jeu.sh` est lancé en root sur le serveur de l'entreprise : Breizhcosystem, qui le sert, ne doit pas pouvoir le remplacer. Une empreinte calculée par Breizhcosystem sur le fichier qu'il sert ne prouverait rien. Dit franchement : qui détient la clé de signature de l'éditeur fait exécuter son code en root sur chaque serveur qui se met à jour ; c'est le seul canal de l'éditeur, et la raison pour laquelle cette clé reste hors ligne (jamais sur Breizhcosystem, ni dans la CI). Prendre Breizhcosystem, son nom de domaine ou son certificat ne suffit pas.

- **Clé de l'éditeur hors ligne** (de préférence clé matérielle FIDO2, `ssh-keygen -t ed25519-sk`), absente de Breizhcosystem et de la CI ; clé publique dans `deploiement/signataires-editeur` (format `allowed_signers`, identité `editeur-living-business`), copiée dans chaque paquet et affichée par le jeu.
- **Publication** : `node scripts/signer-publication.ts --nexus … --cle …` sur le poste de l'éditeur revérifie chaque zip contre `SHA256SUMS.txt` (celui de la CI sur tag, de préférence), inscrit dans l'installateur la version, le nom et l'empreinte SHA-256 du paquet Linux, la clé publique et l'adresse de Breizhcosystem (plus aucun marqueur que Breizhcosystem réécrirait), puis le signe (`ssh-keygen -Y sign`, espace de noms `living-business-installateur`, signature en dernière ligne). `SHA256SUMS.txt` est signé aussi (`living-business-paquet`). Le script refuse une clé absente des signataires et revérifie la signature comme un serveur avant d'écrire quoi que ce soit.
- **Sur le serveur** : l'installateur n'utilise plus la liste de Breizhcosystem (`/v0/telechargements`) : il installe le seul paquet dont l'empreinte est signée, version et nom vérifiés (`X.Y.Z` stricts et accordés, aucune traversée de dossier), extrait dans le dossier attendu ; il refuse une version plus ancienne que celle installée (`LB_RETOUR_ARRIERE=1` pour un retour volontaire). Il enregistre la clé de l'éditeur dans `/etc/living-business/signataires` (root, 0644).
- **Un numéro = un paquet** : registre `deploiement/publications-signees.txt` (refus d'un autre paquet sous un numéro publié, ou d'un numéro plus ancien) ; sur le serveur, chaque paquet va dans `versions/<version>-<empreinte>` : un paquet corrigé n'est jamais ignoré parce que son numéro existe déjà.
- **Mise à jour** (`sudo living-business-mise-a-jour`) : télécharge le script dans un dossier temporaire privé, vérifie sa signature avec la clé **enregistrée sur le serveur** (pas celle que fournirait Breizhcosystem), et ne l'exécute qu'ensuite ; sinon rien n'est exécuté. Le modèle non signé (dépôt, paquet téléchargé) fait de même avec la clé enregistrée ou, à défaut, celle qu'il contient.
- **Première installation** : le jeu (Réglages → Mettre en ligne) donne une commande qui vérifie la signature avec la clé qu'il connaît avant de lancer le script. Sans clé connue, la première installation repose sur la confiance dans le canal HTTPS de Breizhcosystem ; les mises à jour suivantes sont vérifiées.
- **Changement de clé** : nouvelle ligne dans `signataires-editeur`, une publication signée par l'ancienne clé (les serveurs enregistrent la nouvelle), puis retrait de l'ancienne. Clé perdue ou volée : voir `docs/conformite/SECURITE.md`.
- Limites connues : les paquets Mac et Windows ne sont pas signés par Apple ni Microsoft (décision à prendre par l'éditeur) ; leur intégrité se vérifie avec `SHA256SUMS.txt` et sa signature.
